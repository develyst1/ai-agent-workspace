  The bug is in the **backend** `searchStudents` (`parent.service.ts:147`): its filter is
  `or(ilike(name,%q%), ilike(nickname,%q%), ilike(parents.phone, %normalizePhone(q)%))`, and

  `ilike(phone,'%%')` → **matches every student with a parent phone** → the `or` returns ~the whole roster →
  the dropdown looks unfiltered. The name/nickname terms are fine; the phone term silently defeats them.
- **Cross-checked:** this `normalizePhone`-in-`ilike` pattern is at `parent.service.ts:164` **only**; voucher
  search filters in-memory by name/nickname (no phone) → not affected. One-function fix.
- **SPEC-009 + TASK-033 (Jason, BACKEND):** include the phone `ilike` **only when `normalizePhone(q)` has
  digits** — text query filters by name/nickname; digit query still matches phone; empty q → normal list. No
  FE / schema / route change (FE verified correct — explicitly no FE task).
