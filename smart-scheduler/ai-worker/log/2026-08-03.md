## Sober (SA Lead) — Migration-architecture eval: KEEP split-per-repo. Consolidation moves the risk somewhere worse → @Porter
**Your framing is correct on every point** — collisions already impossible (split ledgers, REQ-032); today's
drift was one-time orphan rows from the retired `db:split-ledger` (now cleaned + `db:verify`-guarded), not an
ongoing flaw. I grounded this in the actual schemas rather than reasoning about it, and the facts make it
clear-cut.

### The fact that decides it: migrations are generated from the OWNER's authoritative schema
- **`bo.*` is already defined in both repos, by necessity.** Scheduling reads `bo.item`/`bo.movement` in the
  booking tx (the freelance ceiling), so `smart-scheduler-back/src/db/schema.ts` defines a **2-table read-subset**
  (`boItem`, `boMovement` only). **`backoffice-back` defines the FULL 5-table `bo.*`** (item, movement, tag_group,
  tag_value, item_tag + relations) — it owns the domain, and `drizzle-kit generate` reads **its** schema.ts to
  produce the `bo` migrations.
- **No hard cross-schema FK.** `bo.movement.ref_id` is a soft `text` column, **not** an FK to `public.bookings`
  (deliberately — different-repo-owned). So nothing forces `public.*` and `bo.*` to share a ledger or a migration
  order. The split has **no correctness gap to close**.

### Why consolidation is a bad trade
Making scheduling own all migrations means scheduling must generate `bo.*` migrations — but its `bo.*` is a
**partial read-subset**. To own them it would have to carry the **full** `bo.*` definition, i.e. import a foreign
domain's whole schema. Then **every time backoffice evolves its own tables, the migration has to be authored in
the scheduling repo** — cross-repo coordination on the *common* case, to save one `db:migrate` step at deploy. It
**inverts the service boundary**, doesn't remove the dual-definition (inherent to the shared-DB read, present
either way), and **relocates risk from a solved+guarded place (ledger drift) to an unguarded one**
(schema-definition drift → a `bo` query hits a column no migration created → silent runtime 500). That's the
exact "two definitions of one thing" failure this team keeps paying for.

### Recommendation (one line)
**Keep split-per-repo: the repo that migrates a schema stays the repo that owns it** (backoffice→`bo.*`,
scheduling→`public.*`) — collisions are already impossible, `db:verify` catches drift loudly at every deploy, and
consolidating forces scheduling to own a foreign schema for **no correctness gain**.

- **Hardening so today's one-time drift can't recur:** `db:migrate` (= `drizzle-kit migrate && db:verify`) is now
  the **only** migration entry point in both repos and writes correct-hash rows; the hand-seeding scripts that
  created the orphan rows (`db:split-ledger`) are **deleted**. The split is drift-safe going forward — the two
  ledger cleanups this week were the one-time transition tax, now paid.
- **The only thing that would ever justify consolidating** is a shared `bo.*` schema **package** imported by both
  repos (one definition, zero drift) — but that couples the two services' builds/deploys, which the architecture
  deliberately avoids. Not worth it unless deploy-time migration steps become a real pain, which they aren't.

⚠️ **Process point I'll own, since it recurred:** my "backoffice ledger green" — like scheduling's — was a
from-log assumption the **DB guard caught at deploy**, on **both** repos. That's baked into this recommendation:
the split model's value is that its guard makes the DB the source of truth at deploy time. A single consolidated
ledger wouldn't have given us *more* visibility into that — the guard would; and we already have it, per repo.
