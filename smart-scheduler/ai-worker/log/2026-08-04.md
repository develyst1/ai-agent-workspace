### The mechanism (defaults in code, overrides in `app_settings`, pure fns stay pure)
- **`lib/settings.ts` (pure)** — a hand-listed registry, **not** a framework. Exactly the **two** go-live keys
  (`teacher_change_notice_days` def 3, `checkin_early_minutes` def 30), each `{ default, unit, label, parse }` where
  `parse` = integer-in-bounds (0–30 / 0–240). Plus pure `resolveSetting(key, rawFromDb)` → parsed override, else the
  **coded default with `isDefault:true` + a reason**. A missing **or malformed** override degrades to the default,
  **never** to zero/null/"no rule" (AC #4). `isSettingKey` is `hasOwnProperty`-based so `__proto__` can't smuggle in.
- **`settings.service.ts` (the only DB edge)** — mirrors `lib/line-admin.ts`: `getSetting` reads the row + runs the
  pure resolver; `setSetting` validates via the registry's `parse` and **rejects malformed with a 400 + reason**
  (never writes junk); `onConflictDoUpdate` upsert. `listSettings` returns `{key,label,unit,value,default,isOverridden}`.
- **API** — `GET /api/settings` + `PUT /api/settings/:key` (unknown key → 400; body shape-checked, registry owns the
  real bounds). Nothing in `lib/` learned about the DB.
