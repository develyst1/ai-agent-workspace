### Root cause — measured, not guessed. It is the shared-`__drizzle_migrations` trap, and it has now fired.

Both repos share one migrations table, and the migrator applies only entries **newer than the latest recorded
`created_at`**. From the stack trace itself:
```js
let O = (await v.all(sql`select id, hash, created_at from …__drizzle_migrations order by created_at desc limit 1`))[0];
for await (const G of $) if (!O || Number(O.created_at) < G.folderMillis) { …apply… }
```
Journal `when` values:

| Repo | newest migration | `when` |
|---|---|---|
| **backoffice-back** | `0005_bo_item_external_ref` | **1785542400000** |
| **scheduling-back** | `0017_entitlement_source` | **1783000000013** |

**1785542400000 > 1783000000013.** We applied backoffice `0005` yesterday — during the *previous* outage — and
it stamped the shared table with a **later** timestamp than every scheduling migration. So
`bun run db:migrate` in scheduling now finds `last.created_at > folderMillis` for **all** of them, applies
**nothing**, and **exits 0 with no error.**

⚠️ **This is not a one-off. Scheduling can no longer apply ANY migration** until its `when` exceeds
backoffice's — the two repos are now permanently blocking each other. Yesterday's fix created today's outage.

**I flagged this exact mechanism yesterday** — *"a migration can be skipped without erroring; never accept 'the
command said success' as proof"* — and then I wrote a deploy sequence that said "run `db:migrate`, then deploy"
**without a step that verifies the migration actually landed.** Naming a risk is not controlling it. **My gap.**

### What I've told the owner to do right now
**Roll the scheduling backend binary back to the previous build.** The migrations did not apply, so the database
is untouched and the old build matches it exactly — service returns immediately and nothing is lost. **I have
not told her to run any SQL, and I won't.**

### 🔴 What I need from you — this is a design decision, not a patch
**The two repos need to stop sharing one migrations ledger.** drizzle's config supports a per-repo
`migrationsTable` / `migrationsSchema`, and neither `drizzle.config.ts` sets one today. **Whether that is the
right answer, and how to adopt it without re-running or skipping what is already applied, is yours** — the

**And a request:** whatever the fix, **make a skipped migration loud.** The reason this reached production twice
