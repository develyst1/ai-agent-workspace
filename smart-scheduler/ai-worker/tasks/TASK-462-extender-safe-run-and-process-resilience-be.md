## §2 Build
1. **A dry run, and make it the DEFAULT for the manual door.** The job reports what it WOULD create — per series: the key, the title, the coach, the dates — and writes nothing. This is the repo's own convention for anything that writes (`ensure-subjects`, `backfill-other-series`, `line-relink-menus` are all dry-run first) and **the extender should have had it from the start — that is my miss in TASK-456's spec, not yours.** The scheduled trigger keeps applying (a nightly job that only ever reports is useless), so: the internal route takes `{ apply: boolean }`, **`apply` defaults to FALSE**, and `sm-jobs/group-series-extender.ps1` sends `{"apply":true}` explicitly — so the nightly run works and a human poking the endpoint by hand cannot write by accident.
2. **Bounds, reported rather than silently enforced:** `maxSeries` and `maxDates` (settings or body, your call) with sane defaults; when a run hits a bound it stops, says so in the summary and in `job_runs`, and the next run continues from where it stopped (it is idempotent by state, so this is free). A first run on an old box should be able to be taken in bites.
3. **The route must not hold the connection open for the whole job.** Two honest options — pick one and argue it: (a) keep it synchronous but make it fast enough by §2.2's bounds; (b) ACK with a run id and let it work, writing the outcome to `job_runs` (the pattern TASK-460 established for the webhook). ⚠️ Whichever you choose, **a long run and a dead process must stop looking identical to the caller.**
4. 🔴 **The process must survive a database blip.** Add a top-level `unhandledRejection` (and `uncaughtException`) handler that LOGS with the reason and keeps serving — an API that dies when the shared cluster hiccups will die again next week for reasons that have nothing to do with us. ⚠️ Say in your report what we lose by not dying (a crash-on-error process can be restarted by a supervisor into a clean state; one that limps can serve from a poisoned one) and pin what a handler must NOT swallow.

## §3 What we lose by not dying — as you asked
A process that crashes on every rejection is restarted by a supervisor into a **clean** state; one that keeps serving can serve from a **poisoned** one. The concrete candidates in this codebase: a module-level flag left set (the outbox's `running`, the extender's `extenderRunning` — both reset in `finally`, so they survive a rejection), a `chatQueues` entry holding a promise that never settles (it clears on settle, and a rejected one now settles), and a pool whose connections are dead (postgres.js discards a broken connection and opens a new one on the next query — see §4). **What the handlers must NOT swallow, pinned:** they may not be silent (N bites), may not `exit(0)` — a supervisor reads that as a clean stop (O bites), the rejection handler may not exit at all (M bites), and neither answers a request. 🚫 Startup failures are untouched by construction: `DATABASE_URL is not set` throws during import, before these handlers exist, and still stops the process.

## §4 For @Otto, via Porter — what the code does when Postgres restarts (🚫 nothing changed)
- The pool is **postgres.js 3.4** with its defaults (`db/index.ts`: `postgres(url)`, no options): up to **10** connections, `connect_timeout` **30 s**, `keep_alive` 60 s, no idle timeout. During a restart every in-flight query **rejects** (`57P03` while in recovery, or a connection-closed error); **there is no retry in our code**. postgres.js does **not** hold a dead connection — it discards it and opens a new one lazily on the next query, so recovery needs no restart of the API once Postgres accepts connections.
- What a supervisor sees: **before this task**, an unhandled rejection anywhere ⇒ the process exits (code 1) ⇒ a restart, or — with no supervisor — an API that is simply gone (consistent with "no HTTP response at all"). **After:** the process stays up and the log shows `[process] unhandledRejection — logged, still serving:` lines with the reason; only a synchronous `uncaughtException` still exits(1).
