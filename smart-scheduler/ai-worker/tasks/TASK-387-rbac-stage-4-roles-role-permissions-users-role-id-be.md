## §1 The model — decided (say if the tree disagrees)
- **A role is LIVE, not a snapshot:** `users.role_id` (nullable FK) references the role; **effective grants = the role's keys ∪ the user's own `user_permissions` rows.** Editing a role changes every holder at their next request (the guard reads per request — no propagation job). A user's own rows are **additive overrides** (extra keys beyond the role). 🚫 No "deny" override this stage — a user who must have LESS than their role gets a different role; named on the list.
- **Tables:** `roles` (`id`, `name` UNIQUE trimmed, `description null`, `created_at/by`, `updated_at`) · `role_permissions` (`role_id` FK cascade, `key`, UNIQUE `(role_id, key)` — the LAST object = the witness) · `users.role_id uuid null` FK `roles` **`ON DELETE RESTRICT`** (the DB refuses deleting a role in use — the service says it first with a count).
- **Delete a role in use: REFUSE with the count** (`409 ROLE_IN_USE "มีผู้ใช้ n คนถืออยู่ — ย้ายก่อนลบ"`); the super admin reassigns first. (SPEC-079 decision, recommended; @Porter carries it to the owner.)
- **Migration header:** `ALTER TABLE users ADD COLUMN role_id uuid NULL REFERENCES roles` takes `ACCESS EXCLUSIVE` on `users` for the statement — a nullable column add is metadata-only (no rewrite), the table is tiny; say it, and that the two new tables lock nothing existing. One run.
