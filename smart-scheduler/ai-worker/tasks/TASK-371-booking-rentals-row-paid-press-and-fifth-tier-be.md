🔴 **Correction 1 — the lock, exactly.** A `CREATE TABLE … REFERENCES "bookings"("id")` takes **`SHARE ROW EXCLUSIVE` on `bookings`** for the duration of the statement: **reads continue, writes (INSERT/UPDATE/DELETE) on `bookings` wait** — and there is NO validation scan (the new table is empty), so the hold is milliseconds. It is not `0033`'s `ACCESS EXCLUSIVE` (which blocked reads too). ⚠️ The same queueing hazard as `0033`, smaller: if a transaction is holding `bookings` when it starts, the `CREATE` queues behind it and every WRITE queues behind the `CREATE`. ⇒ the header says **"not closed-shop; a write-blocking blink on `bookings` — run it outside the 17:30 end-of-day job and not while an import is running"**, never "it takes 5 ms". One run, one transaction, both statements; `IF NOT EXISTS` on both ⇒ rerunnable.
🔴 **Correction 2 — the witness must be the LAST object, invented by this migration.** `0034`'s rule: probe the last thing created, and it must exist ONLY because this ran. So the UNIQUE is not an inline constraint (its index would be named by Postgres) but the migration's **last statement, `CREATE UNIQUE INDEX IF NOT EXISTS "booking_rentals_booking_uq"`**, and that index is `0035`'s witness in `migration-witness.ts` (`kind: "index"`, `rerunnable: true`). **Tag `0035_booking_rentals`** — counted now: `drizzle/*.sql` = 35 (0000–0034), journal = 35, newest `0034`, so this one is `0035`; the count becomes **36 = 36** (your "migration 36" is the 36th file; its tag is `0035`, as `0034` was the 35th).
🔴 **Correction 3 — how an existing box gets the 5th `bo_item`: `bun run sale:ensure-items`, and nothing else.** The script is ADDITIVE (creates what is missing, never overwrites a price) and `recordSale`'s own unknown-code log already says *"add it there and re-run `sale:ensure-items`"* — the mechanism exists and names itself. 🚫 Not a migration insert: `bo.item` is the backoffice's table and this repo's migrations do not write it. **Deploy step order: migrate → `sale:ensure-items` → restart.** If a paid press lands before the script runs, `recordSale` answers `skipped: no-item` ⇒ `502 RENTAL_NOT_POSTED`, the row stays unpaid, the press is retried after the script — the backstop the contract already names.
🔴 **Correction 4 — the UNIQUE's `23505` must be caught in the SERVICE.** `index.ts`'s `onError` renders every `23505` as **`409 SLOT_TAKEN "มีคาบในช่วงเวลานี้แล้ว"`** — a second rental on a session would answer *"the slot is taken"*. The insert catches `23505` and throws `409 RENTAL_EXISTS` (the TASK-364 shape: the constraint is the guard, the service is the sentence).
🔻 **Correction 5 — the DTO's `rental` needs no grouped read of its own.** The row is a RELATION (`bookings.rental: one(bookingRentals)`), so it rides in `withBookingRelations` — every relational reader (calendar grid, the tray, the single read, check-in) gets it in Drizzle's one batched relation query, no N+1 and no per-reader plumbing; `toBookingDTO` maps `b.rental` itself. The ONE hand-written select (`getBookings`, the paginated list) gets a grouped `rentalsByBooking(ids)` read spread onto the row, exactly as `additionalTeachersByBooking` already is. `bookingsWithRentals` (the ledger join that fed `hasRental`) goes with it — dead the moment its only reader is gone.

✅ **The remark rule: "set + ride".** The customer's *"Full Set or inline"* — inline skates are the ride item (`rental-ride` = *"ride only"*); a full set is `rental-set`. Both need a remark (which pair / which size); helmet, pads, helmet+pads do not. Pinned by code.
✅ **`BOOKING_NOT_LIVE` = `CANCELLED` or `PAUSED`** — the two statuses the grid hides; a delivered session (`ATTENDED`) still accepts a rental (the cash is collected at the shop, sometimes after). Pinned.
✅ **Paid twice ⇒ `200`, no second post:** the service returns early on `paid_at` set (no call), AND `recordRental`'s key `rental:<bookingId>:<code>` makes a second call a `duplicate` — both asserted, as you asked.
📌 **Your owner's-list question, answered by the tree: a cancelled session KEEPS its rental row.** Cancel is a status write, never a delete; the cascade fires only on a hard delete of the booking, and no path deletes a booking. A paid row on a cancelled session stays paid (the money is posted; the backoffice reverses if it must), and with `includeCancelled` the tray shows it green. Nothing to build — the simplest is what the schema already does.
