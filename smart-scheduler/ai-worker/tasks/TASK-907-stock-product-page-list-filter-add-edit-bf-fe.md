### Your 4 write-shape questions — answered (no invention; grounded in REQ-120)
**Q1 — the real create/edit route + body.** It is NOT in 904 (that was import + 2 reads). I've cut it as **TASK-911** (BB product create/edit write); build your fixture to this so it wires on arrival:
- `POST /v1/stock/products` (CEO) body `{ code, name, category, priceSatang, commissionGroup: string|null, active, openingQuantity }` → creates a `bo.item` (source `stock`, direction INCOME, ceilingQty NULL, remainingQty via ONE opening movement, category tag, `commission_group` = the name).
- `PATCH /v1/stock/products/:id` (CEO) body `{ name?, priceSatang?, category?, commissionGroup?, active? }` — field edits, **no movement, never changes the balance** (balance moves only via import / a stock-out / an explicit adjustment).
- **One change to your fixture: DROP the per-product commission AMOUNT.** Commission is **per GROUP** (REQ-120 R3.1 + O12 Khwan 10-15: groups carry the rate, e.g. Miller helmets 40 separate from Animal Helmet 40). The product carries only the group **name**; the amount lives on the group, which is a future managed-groups task. So the form sets `commissionGroup` = a name (pick-existing or type); show the amount as "—" until groups-with-rates lands. (Bob's `GET /stock/products` already returns `commissionGroup:{name, amountSatang:null}` — the null is correct.)
**Q2 — Model code editable after create? NO — read-only, your call is right.** It is the product's identity and the **import match key** (`external_ref`); changing it would break import matching. A code change = deactivate + create new.
**Q3 — are commission groups a managed list on BB? YES in the requirement (per-group rate), but the managed-groups feature is NOT built yet.** For now: free-text/pick-existing group **name** on the product, **no amount** (see Q1). When the groups-with-rates task lands, the picker becomes a managed list and the rate comes from the group. Don't build a per-product amount.
