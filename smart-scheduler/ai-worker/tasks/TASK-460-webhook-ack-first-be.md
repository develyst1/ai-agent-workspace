## §1.2 🔴 The ordering question — my answer, and the argument you asked for
**I will put in the per-chat lock.** But the argument matters, because it changes what the lock is FOR:
- **ACK-first does not create the concurrency.** Two rapid messages from one chat already arrive as **two separate HTTP requests**, each running `handleMessage` concurrently — nothing serialises them today. A batched delivery (several events in ONE request) is already sequential in our loop and stays sequential after the change.
- What ACK-first genuinely changes is that our work continues **after** the response, so a second request can interleave with the tail of the first — which is **exactly what already happens whenever the first request is slow**, i.e. precisely the 14 cases in the console. So the risk is **unchanged in kind, and today's version of it is the one that is actually firing.**
- ⚠️ What DOES get worse is the **visibility**: today a mangled state machine came with a `request_timeout` in the owner's console; after this change everything returns 200 and a lost step looks like nothing at all. **A failure mode that stops leaving evidence is worse than one that fails loudly**, even at the same rate.
⇒ Therefore: a **per-chat queue keyed on the LINE user id** (a `Map<lineUserId, Promise>` chain — the next event for that chat waits for the previous one's tail, other chats are untouched), plus the never-silent logging below. ~15 lines, no infrastructure, and it removes the class rather than arguing about its probability.
🔴 **The honest limit, stated: this serialises within ONE process.** The repo does not record how many the API runs as (no `ecosystem.config`/PM2 file is committed here — that is the server's, Otto's). With N processes it degrades to exactly today's behaviour, so it is **never worse than now**, but I will not claim it is a distributed lock. If the box runs more than one instance, the DB-level answer is a `pg_advisory_xact_lock` — and I am NOT proposing that here, because the handler makes two outbound HTTPS calls and holding a transaction across those is a worse trade than the window it closes. 👉 Ask Otto how many processes serve `/api`, and I will say in the report which of the two we actually have.
