## Unsorted — 2026-08-19

**Migration ledger — how drizzle actually behaves here**
- 🔴 **`drizzle-kit` reports "migrations applied successfully" on a night the ledger is broken. Only `db:verify`
  disagrees.** A ledger missing rows makes drizzle **silently skip** migrations later (observed on `uat`,
  2026-08-19; the same trap hit prod on 08-02).
- **Only a WITNESS-BASED check can tell "the schema really has it, the ledger just doesn't know" from "it was
  never applied"** — `db:seed-ledger` (`scripts/seed-ledger-from-schema.ts`) is **dry-run by default,
  schema-is-source-of-truth, self-halting, and NEVER modifies the shared `drizzle.__drizzle_migrations`**, which
  is kept as evidence and rollback (Sober, 2026-08-19).
- **A schema can be correct while the ledger is behind.** `uat`'s verify failure was **not** a missing `0018` —
  `0018` had landed and its witness was present; four *older* migrations were missing ledger rows (corrected on
  the record, 2026-08-19, after the team had been saying "two migrations behind" for two days).
- **A wipe+import writes ROWS and runs NO DDL, so it depends on the current schema, not on the ledger** — the
  ruling that unblocked go-live (Sober confirming Porter's read, 2026-08-19). Same reasoning makes `db:reset`
  safe on a box with a bad ledger.

**Operating the `sid` box**
- 🔴 **An orphaned backend process survives a machine restart and holds its port.** Symptom: **every backend
  crash-looping with `EADDRINUSE` while every frontend is healthy** — including other projects' backends at
  ~5,000 restarts. `pm2 reset` only zeroes counters and `pm2 restart` just spawns another process that cannot
  bind (observed, 2026-08-19).
- 🔴 **A frontend talking to an orphaned PRE-DEPLOY backend produces `Cannot read properties of undefined (reading
  'find')` inside an `Array.map`** — new FE code reading a field the old payload never sent. DEF-4 was diagnosed
  from the deploy state, not the stack trace, and needed **zero** code change (Porter, 2026-08-19). **Check what
  is actually serving the port before debugging a bundle.**
- 🔴 **`pm2` is itself a Node process: killing every `node`/`bun` without `pm2 save` first takes the daemon AND its
  app list with it.** It happened — the list was lost and recovered only because the owner had pasted `pm2 ls`
  into chat earlier that day (2026-08-19). Order: `pm2 save` → `pm2 kill` → end strays → `pm2 resurrect` →
  `pm2 ls` → **`pm2 save` again immediately**.
- **An offhand terminal dump in chat became the only inventory of that server, because nobody kept one anywhere
  else** (Porter's own note, 2026-08-19).

**The customer's student file — quirks that will still be true next month**
- **Column A (the day) is a MERGED CELL per day-group**, so a CSV export carries the day on the block's **first
  row only**; every other row is empty. A naive filter selects 1 row for a 9-row day and reports success
  (observed, 2026-08-19).
- **The CSV header spans TWO physical lines** — the `Gender` field contains a newline — so a line-counter is off
  by one for every row; parsed as proper CSV records, **record #2 = xlsx row 2** with `--header-rows 1`
  (Porter, 2026-08-19).
- **Excel writes phone numbers as `8.6E+08` unless the column is formatted to full integer digits before
  Save-As CSV UTF-8** (Sober's operator note, 2026-08-19).
- **A self-consistent report can still be wrong.** The lesson stated twice that day: a batch's expected size must
  be checked **against the file**, from outside the batch, or an empty-ish batch looks successful.
