## Unsorted — 2026-08-11 (deploy & platform behaviour)

- 🔴 **GUI SQL tools use a SEPARATE CONNECTION PER RUN.** The owner's VS Code SQL tool auto-rolled-back a `BEGIN … DELETE` batch that had no `COMMIT` in the same run, and the `COMMIT` he ran afterwards hit a connection with no open transaction (a silent no-op) — **nothing was deleted and it looked as if it had been.** ⇒ **a multi-statement transaction must be run as ONE selected batch, or in the server `psql` CLI (a persistent session)** (observed, 2026-08-11).
- ⚠️ **A screenshot is not a fresh query.** The "the delete did not persist" alarm on 2026-08-11 turned out to be an **old screenshot the owner copied by mistake**; a fresh query in the same psql session showed the clear had committed. ⇒ confirm state with a fresh read, not with an image (observed, 2026-08-11).
- **GATE 0 of any customer-prod deploy = a VERIFIED non-zero backup.** Four earlier `sm-prod-backup-*.dump` files were **0 bytes — failed attempts**. A good dump is CUSTOM/gzip and is verified read-only with `pg_restore --list` (schema + all TABLE DATA sections + the right dbname) (Porter, 2026-08-11).
- **`db:backup`'s "0.0 MB" print is just rounding a genuinely small database — it is not a failure signal.** A 37 KB dump was a complete, valid backup (observed, 2026-08-11).
- **There are THREE migration ledgers in the DB and a reset must never touch any of them:** `drizzle.__drizzle_migrations_scheduling`, `drizzle.__drizzle_migrations_bo`, and the retired default `drizzle.__drizzle_migrations` (kept as evidence/rollback) (Sober, 2026-08-11).
- **`db:seed-ledger` is dry-run by DEFAULT, witness-based (the schema is the source of truth), idempotent, self-halting, and never modifies the old `__drizzle_migrations`.** It is the sanctioned fallback when a box has the tables but not the split ledger (Porter, read from the script before running it on prod, 2026-08-11).
- **A box that already has the schema but an empty split ledger will make `drizzle-kit migrate` try to re-apply `0000` and fail on existing objects.** That is the EXPECTED transition case, not a defect — the witness `db:seed-ledger` fallback is the answer (observed on customer-prod, 2026-08-11).

## Unsorted — 2026-08-11 (frontend platform quirks that cost real defects)

- 🔴 **Tailwind v3: a colour token defined as a bare `var(--x)` CANNOT carry an alpha modifier.** `bg-token/NN` is then **never generated at all** — the element paints `rgba(0,0,0,0)` with **no error**. **The fix shape is RGB channel triplets in the CSS var + `rgb(var(--x) / <alpha-value>)` in the Tailwind config.** This broke 6 sites (the app header backdrop among them) on 2026-08-11 and would have silently broken every future `/NN` use of those tokens.
- **Consequence of the triplet form:** any *raw CSS* use of those vars must be wrapped in `rgb(...)` — a bare channel-triplet var is an invalid colour. DoD grep: no bare `var(--color-` outside `rgb(` (Sober + Fern, 2026-08-11).
- **`transition-property: all` with `transition-duration: 0s` does not animate anything.** The question is whether an element animates, not what its property list says — this produced a false FAIL that QA retracted (Tanya, 2026-08-11).
- 🔴 **A synthetic probe only proves something about a class Tailwind actually generated.** A class that only ever appears as `hover:bg-x/NN` generates `.hover\:bg-x\/NN:hover` and never the bare class, so a hand-made `<div class="bg-x/NN">` is guaranteed to paint nothing whether the product is broken or not. **Check the source usage and the variant before concluding the product is broken.** Tanya's third time hitting this shape; she wrote the rule into `REGRESSION.md` on 2026-08-11 (📌 already homed there — recorded here only because it is a durable platform truth).
- **The STANDING RULE width set is 1600 / 1280 / 768 / 375** (the defect it exists for was a control collapsing to 26/36 px) (observed, 2026-08-11).
