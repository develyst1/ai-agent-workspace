## Product limits

- 🔴 **There is ONE SHARED STAFF LOGIN. The product cannot attribute an action to an individual.** Every history event carries `actor = null` by design (SPEC-035 §1); *who* did something is recorded only where a dedicated column exists (e.g. `ended_by`) and is answerable only by query (2026-08-24).
- **The system never verifies that cash was collected — not even for a manually marked `ATTENDED`** (Sober, 2026-08-24). Revenue posting is a bookkeeping event, never a proof of payment.
- **`PATCH /courses/:id` accepts exactly ONE field — `adminUnlocked`. `size` is NOT editable**, deliberately: reducing `size` would corrupt the record of *what the family bought* (the REQ-064 lesson) (2026-08-24).
- **Cancelling a course's sessions one at a time can never end a course — they grow back.** `reconcileCoursePlan` re-owes a make-up for every course-session cancel by design. This was watched happening to a real family on 2026-08-24.
- **`course:cleanup` refuses anything that carries a posted sale — and every bought course has one.** It is not a way to remove a course (2026-08-24).
- 🔴 **An appended `EXTENDED` make-up is a REAL future booking: it blocks its slot and it shows on the calendar.** Only `CANCELLED` is hidden by `getCalendar` and treated as slot-non-blocking. ⇒ **every course that has ever taken a sick-leave carries a live make-up sitting on some teacher's calendar** (Sober, 2026-08-24 — caught as a would-be silent-ship defect).
- **`returnsConsumedUnit` is `ATTENDED`-only** — so cancelling a `NO_SHOW` row returned no unit *and* appended a make-up nobody bought ("the strictly worse path"). 📌 Fixed only as a side-effect of killing `NO_SHOW`; the helper itself was never widened (2026-08-24).
- **Pressing `มาเรียน` on a row that is already `ATTENDED` is a no-op** (`if (current.status !== "ATTENDED")`) — which is what makes the auto-attend design safe against double-consumption (2026-08-24).
- **An ended course does not visibly look ended on the plan screen** — the plan just comes back empty, so a cancelled course reads like a finished one. Re-booking is server-guarded (`insertable=false`), so the gap is informational only (Fern, 2026-08-24; cut as a follow-up).
- **The attendee note is capped at 200 characters and is explicitly NOT for PII**; **course creation deliberately does not offer it** — the note is per-session only, because "who is bringing the child this hour" is inherently per-session (Fern's call, SA-accepted, 2026-08-24).

## Unsorted — 2026-08-24 (lessons that will still be true next month)

- 🔴 **`db:migrate` can print "migrations applied successfully", exit 0, and leave the schema broken.** On 2026-08-24 `0022_booking_attendee_note` read **`not-applied · column found=false`** *after* a successful-looking migrate, because the ledger held a row newer than the migration — the **documented TASK-085/086 failure mode**, and the second outage it has caused. **The deploy looked fine and was not.** ⇒ **`db:verify` — not `db:migrate`'s exit code — is the only proof.**
- **The repair sequence for that state: `db:seed-ledger` (dry-run → `--apply`) → `db:migrate` → `db:verify`. Seeding FIRST is what lets `migrate` see the missing migration at all** — the tool says so itself (*"After seeding, db:migrate would apply: 0022"*) (2026-08-24).
- **Deploying code without its migration takes the customer's calendar down on every box at once** (`GET /api/calendar` → 500). It was diagnosed in ~2 minutes from `git show --stat` on the newest commit — **the diff named the missing migration; no log-reading was needed** (2026-08-24).
- 🔴 **Derive the truth from an invariant, not from an audit trail you no longer have.** The owner's `UPDATE … NO_SHOW → ATTENDED` had already erased which rows were which — and it did not matter: because `COURSE_DELIVERED` counts `ATTENDED` and `NO_SHOW` alike, `stored − prior − delivered` located **both** damaged courses exactly, with nothing left over. **Kept deliberately as a reusable technique** (Porter, 2026-08-24).
- 🔴 **A counter that has always read zero may be hiding a defect, not proving safety.** `courses_cut` was 0 on every run on both boxes until 2026-08-23, and that "unexercised" gap was concealing a real double-consume defect that could not surface until the cut ran on real bookings (Porter, 2026-08-24).
- **Do not read a table taken before an event as evidence about the event.** Porter's "the 08:00 digest did not fire" alarm was wrong for one plain reason: **the owner ran the query before 08:00** (2026-08-24).
- 🔴 **A test can assert the bug.** Jason's own test asserted that `EXTENDED` stays untouched, so a green suite would have shipped a ghost make-up holding a teacher's slot on the commonest path there is. **Third time on this project** — Onewheel's 10 h, bike/skate's 1 h, now this — and the common thread every time is **a test written from the code's intent rather than from what the user would see** (Jason, 2026-08-24).
- 🔴 **Compiler-silent allow-lists in response mappers are a recurring defect class — third occurrence on one feature set** (`createBooking`'s POST body, `dtoToBooking`, `toSessionRow`). Request bodies are guarded; **nothing guards the response mappers.** The structural fix adopted: **type the mapper's return as the contract type, so the next dropped field is a compile error rather than a silent 500** — stronger than a test, and it cannot rot (Sober's ruling, 2026-08-24).
- **A check LEAVING the attention registry is as legitimate a move as one arriving** — a line that is structurally always zero teaches everyone to skim past the ones that are not (Jason, 2026-08-24, deleting the dead NO_SHOW digest check and moving the registry count test 11 → 10).
- **A constant that must mirror another set should BE that set, not a hand-written copy of it** — `ENDABLE_STATUSES = COURSE_LIVE_STATUSES` so the next status anyone adds cannot drift away from it (2026-08-24).
- **When an irreversible action shows a count, the count must be the SERVER's — never client-computed.** For the course-cancel dialog *"the number in that sentence is the entire safety mechanism"*, the preview is re-fetched on every open (a cached preview could describe a plan that has since changed), and the action is structurally bound to its own course id (2026-08-24).
- **Deleting a bad state deletes its whole family of bugs.** Killing `NO_SHOW` fixed three separate defects at once — the false label, the double-consume, and the cancel-that-returns-nothing — and Porter verified this by checking rather than asserting (2026-08-24).
