### 📏 STANDING RULE — FE layout IS verifiable here (learned 2026-08-01, TASK-081)

**We were wrong that the in-app browser can't check layout.** The pane doesn't *paint*, but it still **computes
layout**: `getBoundingClientRect()` returns real widths and `resize_window` genuinely reflows the page. Fern
reproduced the REQ-024 date-input defect **by measurement** — the two inputs were **26 px and 36 px** where the
fix gives **176 px**, which is the stakeholder's screenshot arrived at from a number.

**So:** any FE change that **adds or resizes a control in a shared row** must **measure the row at 1600 / 1280 /
768 / 375 and report the numbers**. That converts "it looks fine" into evidence.

**Still out of reach:** colour, contrast, overlap, font rendering — anything *painted*. **A deployed look
remains the only full detector**, which is an argument for deploying in small slices rather than for reviewing
harder. (Sober had told the team layout was structurally unverifiable and to compensate with prose; that was
wrong, and this rule replaces it.)

### 🔴 MIGRATION CHECK — read this before every single deploy. No exceptions.

**2026-08-01: the production site went down (`GET /teachers` → 500, every `bo.item` query dead) because this
manifest said "✅ no DB migration in this batch".** That was true when written. **TASK-066 then added
`0005_bo_item_external_ref` and nobody updated this line.** The stakeholder deployed trusting it, the new code
queried a column the database didn't have, and the frontoffice was unusable until the migration was run.

**The rule, and why it is phrased this way:**

> 🔴 **"No migration" is a CLAIM, not a state. It expires the moment another task lands.**
> **Nobody may write or repeat it without re-counting the migration files at that moment.**

A "nothing to do here" line is the single most dangerous cell in this table, because it is the one people act on
**without checking**. Every other row invites verification; this one invites trust.

**The 10-second check — run it before any deploy** (needs no database access):

```bash
ls H:/scheduler/smart-scheduler-back/drizzle/*.sql | wc -l          # vs "tag" count in meta/_journal.json
ls H:/scheduler/smart-scheduler-backoffice-back/drizzle/*.sql | wc -l
```

- **File count must equal the `"tag"` count in that repo's `drizzle/meta/_journal.json`.** A `.sql` file missing
  from the journal is **silently skipped** by `db:migrate` (TASK-042).
- Then compare the newest file against what is already applied on the server. **If a newer migration exists,
  this batch HAS a migration** — say so in the table, and run it **before** restarting the app.
- ✅ **Audited 2026-08-01 after the outage: scheduling 15 = 15, backoffice 6 = 6. No unregistered migrations.**
- ✅ **Re-audited 2026-08-03 (Sober, deploy-gate) on branch `dong`: scheduling `.sql` 18 = 18 journal tags, backoffice 6 = 6. No unregistered migrations. Split ledgers confirmed in both `drizzle.config.ts` (`__drizzle_migrations_scheduling` / `__drizzle_migrations_bo`); `db:migrate` = `drizzle-kit migrate && db:verify`, and `verify-migrations.ts` exits 1 on a silent skip.**

**Two commands, and they are NOT interchangeable — Porter got this wrong live, during an outage:**
| Command | Repo | What it does |
|---|---|---|
| **`bun run db:migrate`** | the repo owning the schema | **Applies the `.sql` schema migrations.** ← this is the one that creates columns |
| `bun run migrate:bo` | `backoffice-back` | **Moves DATA** `ops.*` → `bo.*`. Creates nothing. Will itself fail if the schema is behind. |

⚠️ Both backends share one `__drizzle_migrations` table, so a migration **can be skipped without erroring.**
**Never accept "the command said success" as proof — load the actual page and confirm.**
