# SPEC-083 — `REQ-097` Teacher login, own calendar (option C: view own · check-in own · report own leave) — feasibility read + build plan (Sober, 2026-09-19)

**Owner ruling (via Porter 09-19):** option C — a teacher logs in and sees/manages ONLY their own calendar: view own sessions, check in own, report own leave. Create / cancel / move stays the admin's.

## §0 What exists (the read)
1. **RBAC option C is live** (`users`, `roles`, grants as boolean keys, ONE `accessGuard` from `route-access.ts` — menu then action, fails closed). A teacher account is an ordinary `users` row + a role. **There is no user ↔ teacher link**: `users` has no `teacher_id`; `teachers` carries `line_user_id` (LINE) and `calendar_token` (the ICS feed) — neither is a login.
2. **"Own" is derivable from existing columns:** `bookings.teacher_id` (the primary, moved on a swap — a GROUP row and its seats both carry it) + `booking_teachers.teacher_id` (extras). The calendar read already filters by teacher for the ICS feed (`calendar.service.ts:60`, `b.teacherId = teacher.id`). **No new column is needed for the predicate — only the LINK.**
3. **Scope today is binary per key** — a grant either opens a route or not; nothing narrows a read. A "scope" is net-new in the guard: one predicate, applied inside the SERVICE reads and writes (not the router — the router cannot see rows).
4. **Check-in** = `PATCH /bookings/:id/status { action: "attend" }` under `action:calendar.status`, plus the public QR scan. **Teacher leave today** = the admin CANCELS the session (status `cancel`) ⇒ the course's make-up appends via the reconcile (SPEC-028 §11.3) and the family is told; the closed reason set is `PROGRAM_CHANGED | CUSTOMER_CANCELLED | ADMIN_ERROR` (`END_REASONS`, required for 1HR/voucher) — **there is no `TEACHER_LEAVE` code** (Porter's memory of a REQ-089 §5 one: it never landed; the cancelled tray was §5.1). Net-new: the code and the teacher-facing act.

## §1 The design (extends option C; one migration)
1. **The link — `users.teacher_id uuid NULL UNIQUE → teachers.id`** (`0044_user_teacher_link`, catalog-only). Set by the super admin on the Users page (create the account, pick the teacher). One user per teacher, one teacher per user. ⚠ §3.1.
2. **Scope = the link, not a grant.** A user WITH `teacher_id` is scoped to OWN by construction; a user without is unscoped (today's admins). *Why not Porter's `calendar:scope = all | own` grant:* a boolean key that must be ABSENT to narrow a read fails OPEN — a teacher account created without the key sees everything. The link fails closed: a linked user is narrowed the moment the link exists, and an admin who also teaches keeps a separate unlinked account (⚠ §3.2). `AuthUser` gains `teacherId: string | null`; ONE `ownScope(user)` predicate = `teacher_id = me OR EXISTS booking_teachers(me)` in `lib/own-scope.ts`, applied in every calendar/bookings READ and asserted in every scoped WRITE — pinned by source (no read builds its own filter).
3. **Where scope bites (BE, fails closed):** `GET /calendar` (the grid incl. `campWeeks` — a linked teacher sees only weeks naming them), `GET /bookings` + `/bookings/:id*` reads (404 outside scope — not 403, the row's existence is not theirs), the reminder/ICS untouched (already per teacher). People/courses/sales/reports menus: a teacher role simply is not granted them (RBAC as today); scope adds nothing there in C.
4. **The teacher's acts (a role "Teacher" the super admin creates once):** `menu:calendar` + `action:calendar.status` **scoped**: a linked user may `attend` only rows in scope, and ONLY `attend` (`confirm`/`sick-leave`/`cancel` refused for a linked user — `403 SCOPE_TEACHER`); the QR check-in (`GET /bookings/:id/checkin`) in scope. **Report own leave = a NEW act `action:calendar.teacher-leave` (55th)**: `POST /teachers/me/leave { date, sessionIds? | all, reason }` ⇒ for each own LIVE session that day (or the named ones): the existing teacher-cancel path — `CANCELLED` + reason code **`TEACHER_LEAVE`** (4th `END_REASONS` code, net-new) + the course's make-up via the reconcile + the family notice the cancel already sends; one transaction; `409` naming a session already delivered. The admin sees the cancelled tray as today; the teacher's leave is an ordinary cancel with a truthful reason. ⚠ §3.3 / §3.4.
5. **FE:** the calendar filtered server-side (nothing to hide client-side — but the teacher picker collapses to "me"); the booking modal in scope shows `Check in` only (create/move/cancel doors absent by key + scope flag from `/me`); a `Report leave` door on the calendar (by the 55th key): a date + tick the sessions (default all) + reason ⇒ one call; the Users page gains a teacher picker on create/edit (super admin). `/me` returns `teacherId` so the FE knows it is scoped (never decides by it).

## §2 Sizes and stages
| stage | what | size |
|---|---|---|
| **C-1 (link + view own + check-in own)** | `0044`, `AuthUser.teacherId`, `ownScope` in the reads + the scoped `attend`, `/me.teacherId`, the Users page teacher picker, the calendar in scope, the modal's reduced doors | **BE M · FE M** |
| **C-2 (report own leave)** | `TEACHER_LEAVE` code, `POST /teachers/me/leave`, the 55th key, the `Report leave` door | **BE S · FE S** |
Total **BE M+S · FE M+S**, 1 migration (`0044`), 1 new key (55), 1 new reason code. C-2 can follow C-1 by a day; both fit one `sid` deploy.

## §3 Decisions for the OWNER
1. **How a teacher account is born:** the super admin creates the user and picks the teacher (recommend) — or self-service via LINE (`teachers.line_user_id` exists — a "claim your login" flow; larger, not C). *Recommend: admin-created; one user per teacher.*
2. **An admin who also teaches:** two accounts (one linked, one not) — recommend; or a `scope-all` override key on a linked user (fails open if mis-granted — not recommended).
3. **Report-own-leave reason:** reuse the cancel with a NEW closed code `TEACHER_LEAVE` (recommend — the tray, the make-up and the family notice all already work off a cancel) — or a separate "teacher leave" status (no: a fifth status touches the slot predicate, the reconcile and every reader).
4. **A leave's reach:** the whole day's own sessions by default with per-session un-tick (recommend), or one session at a time only.
5. **A group's swapped teacher:** sees the group and its seats from the swap date on (the row's `teacher_id` moved with the swap — by construction); the previous teacher stops seeing them. Confirm that is the wanted reading.
6. **Advance-notice rule for a teacher's leave:** none in C (the admin's leave-override rule is for families); a same-day leave is allowed and the families are told. Say if a cut-off is wanted.

## §4 Non-goals (C)
No create/move/cancel by a teacher; no teacher-side sales, people or reports; no LINE login; no change to the ICS feed or the reminder; no scope on the backoffice.
