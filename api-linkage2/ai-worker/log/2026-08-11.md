## [14:39] Sober (SA Lead)
- Picked up REQ-001 (READY_FOR_SA, urgent). Set it **IN_SPEC**. Read the evidence
  transcription and then the real code in all four repos (read-only, no changes).
- **The REQ's premise is wrong in a way that matters.** The services are not
  ignoring forwarding headers — `RequestAuditFilter.getClientIp()` already reads
  `X-Forwarded-For`, and it is **byte-identical in all four services**
  (`RequestAuditFilter.java:136-140`; verified by diff). All four also set
  `server.forward-headers-strategy: native` in `application.yml`.
- Root cause as far as code can tell it: **two IP resolutions run per request and
  fight each other.** Tomcat's `RemoteIpValve` (switched on by that `native`
  setting) consumes the forwarding headers, rewrites `getRemoteAddr()`, and
  modifies/removes `X-Forwarded-For` on the way. Our filter runs *after* the valve,
  re-reads the raw header, and overrides the valve's answer with `split(",")[0]`.
  The filter therefore cannot tell "I found the caller" from "I re-read a leftover
  proxy address", and falls back to `getRemoteAddr()` — the nginx/Docker peer. That
  is the reported `10.32.1.60`.
- Two more defects in the same three lines, both independent of topology:
  leftmost `X-Forwarded-For` is **caller-supplied and therefore forgeable** (this
  field is audit evidence — a caller can currently write their own IP into it), and
  the filter **silently substitutes our own address** when it cannot determine the
  caller, which REQ-001 requirement 3 explicitly forbids.
- Wrote `specs/SPEC-001-caller-ip-in-audit-log.md` (DRAFT): single deterministic
  resolution in the filter (`forward-headers-strategy: none`), right-to-left walk of
  `X-Forwarded-For` against a configured trusted-proxy list, literal `UNKNOWN` when
  the caller genuinely cannot be determined. No API, DTO or data-model change.

  peer is one of our hops do we walk the chain. Under the real topology the peer is
  always one of our private hops, so **production behaviour does not change** — it only
  closes the bypass path.

  address**: an explicit narrow list records their real address; the built-in default would
  treat them as one of our hops and believe their header. Whether that path exists is REQ-001
  **Q9**, still unanswered.
- **Why I recommend it anyway:** the comparison is not "default versus narrow list". A
  deployment that hits this path has **no list at all**, and with no list nothing is trusted,
  the peer is returned, and the front server's IP lands in the audit log — REQ-001's original
  bug, silently. Against that, the default is a clear improvement, and anyone wanting the
  stronger guarantee sets the list explicitly and loses nothing.
- **The part of the design I care most about:** when the built-in default is used, the service
  logs a `WARN` at startup naming the ranges. "Correct by default" must never quietly become
  "wrong by default and nobody noticed" — today's entire incident was a wrong audit value that
