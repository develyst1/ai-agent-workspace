### The rule, end to end — implement exactly this
For each printed line on the form, which carries its own hardcoded `CHECKLIST_CODE`:

```
report line  ──has──▶  CHECKLIST_CODE   (e.g. "ReqMove00013" = ส.ค.4)
                            │
                            ▼
        T_S_REQUEST_CHECKLIST  WHERE CHECKLIST_CODE = <that code>      → its ID
                            │
                            ▼
        T_T_REQUEST_DOC  WHERE REQUEST_ID = <request>
                          AND REQUEST_CHECKLIST_ID = <that ID>
                            │
                            ▼
        tick  ⟺  such a row exists
                 AND ATTACH_FILE_ID IS NOT NULL AND ATTACH_FILE_ID <> 0
                 AND STATUS <> 'D'
```

Anything else ⇒ **no tick**. `IS_ACTIVE` plays no part at any step.

**Direction matters and is the thing I got wrong twice:** we start from the **report line's code** and
ask whether a matching document exists. We do **not** start from the request's documents and try to
work out where each one belongs. The form is the driver; the data only answers yes/no per line.

`CHECKLIST_CODE` already carries its group prefix (`ReqMove…` / `ReqSaleDom…` / `ReqSpecial…`), so a
lookup by code alone is unambiguous across groups — no group filter needed, though adding one is
harmless.

- Resolve code → ID **once per report** (a single `IN` query over the form's codes), not per line —
