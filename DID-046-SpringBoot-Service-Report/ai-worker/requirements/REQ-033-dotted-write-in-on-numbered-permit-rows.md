# REQ-033: `(1)/(2)` permit rows must render as label + dotted write-in, like every other write-in

- Status: READY_FOR_SA
- Priority: MEDIUM (cosmetic on paper, but it is a government form)
- Requested: 2026-08-31 by human
- Scope: **อ.9 transport · อ.14 · อ.15 · อ.4** — four forms. **อ.9 destroy is NOT in scope.**

## Problem
Two different mechanisms produce write-in fields, and only one of them draws the dotted line:

| mechanism | dotted line | example |
|---|---|---|
| template renders **label + its own field** | ✅ yes | `เลขที่ 3540400188066` · `ลงวันที่ ............` |
| **builder concatenates a string** and the template prints it as one label | ❌ no | `(1) ที่ x/xxxx  ลง 1 ม.ค. 69` |

The second case is a single composed string, so there is no separate value field to underline. When
the data is empty it prints `(1) ที่    ลง` — a bare label with nothing to write on.

## Requirement
Render the `(1)/(2)` rows the same way as the rest of the form: **label · dotted write-in · label ·
dotted write-in**.

- **Empty** ⇒ the dotted line still prints, so an officer can fill it in by hand.
- **Populated** ⇒ the value prints **on** the dotted line.

Match the existing style already used elsewhere on these same forms — this is not a new design.
Do not restyle the write-ins that are already correct.

## Acceptance Criteria
- [ ] On all four forms, `(1)/(2)` rows show a dotted write-in after `ที่` and after `ลง`.
- [ ] Empty ⇒ dotted line visible; populated ⇒ value sits on the line.
- [ ] Write-ins that already render correctly are **unchanged** (`เลขที่` / `วันหมดอายุ` /
      `ลงวันที่` / `ออกให้เมื่อ`).
- [ ] อ.9 **destroy**, อ.6, a1, a3 and the other builders are untouched.
- [ ] No literal `null`; structure, order and labels otherwise unchanged.

## Constraints
- `.jasper` is generated by the build now (REQ-031) — no manual regeneration, but **verify on a
  rendered PDF**, not on the source.
- The four forms are DELIVERED and QA'd; this is a visual change to shipped output, so each needs a
  re-render check.

## Note on how this was scoped
I first reported that อ.9 destroy also needed fixing. **That was wrong**, and the stakeholder caught
it by rendering the form and showing me the dotted lines were already there. My check had searched for
the *labels* (`เลขที่`, `วันหมดอายุ`) rather than for the *dotted lines* — it answered a different
question from the one being asked, and it would have sent the team to edit a template that was fine.

The distinction that actually matters is **template-field vs builder-concatenated string**, which is
invisible to a text search and obvious the moment you look at a rendered page.
